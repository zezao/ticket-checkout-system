# Baseline — 2026-11-24

Application commit: `ceea519` (Phase 4). The benchmark harness, seed, Compose
profile and this report are the Phase 5 change set; the API and worker code did
not change for this baseline.

| Go | 1.27.3 |

| PostgreSQL | `postgres:17-alpine` |
| Redis | `redis:7-alpine` |
| Load | 50 constant VUs, 30 s per scenario, no think time |
| Benchmark event | 1,000 seats, `0199b000-0000-7000-8000-000000000001` |

All processes run in containers on the same host: PostgreSQL, Redis, API,
worker, k6. The monitor samples every ~1-2 s (16 samples per run): API
`pgxpool_acquired_conns`, cumulative pool wait, worker `outbox_lag_seconds`, and
`docker stats` CPU for the PostgreSQL container.

## Command

```sh
docker compose up -d --build
BENCH_VUS=50 BENCH_DURATION=30s make bench
```

Each scenario resets the benchmark event, deletes its Redis seat-map key, stops
and restarts the worker, then runs k6 in the Compose network.

## Observations

- **Hot seat.** 5,042 hold attempts/s but only 67 successful hold+release
  cycles/s. The single seat row lock serializes the winners; 98.7% of attempts
  wait and return 409. The pool is fully saturated (25/25) and the cumulative
  pool wait grows by 488 s in 30 s. PostgreSQL uses about 4.4 cores. The p99
  hold is 23.5 ms even though the successful path is short, because losers queue
  behind the row lock and the pool.
- **Uniform and skewed.** More seats means fewer conflicts and more success:
  about 2.4k and 2.2k successful cycles/s. The API sustains about 4.9k HTTP
  requests/s (hold + release) with a p99 of 23-27 ms. The pool is still fully
  saturated and PostgreSQL uses 4-5 cores; the wait delta is ~520 s per 30 s.
- **Outbox relay is the event-stream bottleneck.** Every successful hold and
  release writes one `seat.changed` row. At 2.4k successes/s that is ~4.8k rows/s,
  while the relay processes at most 100 rows/s (100 per one-second tick). The
  lag reaches ~26 s in 30 s. Holds and payments are unaffected (the outbox insert
  is inside the transaction), but cache invalidation and downstream consumers
  fall behind.
- **Seat map.** The seats are served from Redis after the setup miss; the
  scenario reaches 3.3k reads/s with p99 46.2 ms. PostgreSQL still uses ~0.5 core
  and the pool peaks at 7 because every request fetches the event row from
  PostgreSQL; only the seat list is cached. Outbox lag is zero.
- **Errors.** There were zero unexpected responses across all runs. The
  1,000-seat benchmark event and unique per-iteration users mean the per-user
  rate limit never fired; the Redis limiter still adds one round trip per hold.

## Bottlenecks

1. **Hot-seat row lock and the pgx pool.** Contention on one seat serializes
   winners; the pool saturates at 25 and the p99 tail is queueing.
2. **Outbox relay throughput.** 100 rows/s cannot drain write-heavy traffic.
   This is a tuning candidate (batch size, interval, parallel relays) and a
   reason to move to a queue later.
3. **Seat-map read path still queries PostgreSQL for the event.** The seat list
   cache does not cover the event lookup; the read path leaves ~0.5 core of
   PostgreSQL work and a higher p99 than the hold path.

## Next experiments (one change at a time)

- Increase outbox batch size/interval or run parallel relays; re-measure lag,
  PostgreSQL CPU and hold p99.
- Tune `PG_MAX_CONNS`; watch whether p99 improves or PostgreSQL CPU becomes the
  limit.
- Cache the event row with the seat map (or combine both in one cache entry);
  re-measure the seatmap p99 and PostgreSQL CPU.
- Try the optional Redis pre-check for hot seats described in the spec, keeping
  the PostgreSQL update as the only arbiter, and publish the before/after
  numbers.

## Caveats

- Docker Desktop/WSL2 shares CPU and memory with the host. Absolute numbers are
  comparable only on the same machine and setup.
- The k6 load generator, API, worker, PostgreSQL and Redis compete for the same
  CPU.
- The monitor samples instead of scraping a real Prometheus server; maxima are
  sample maxima.
- The mock payment provider is not involved in these scenarios.
- These are baselines, not pass/fail targets.

## Reproduction

```sh
docker compose up -d --build
BENCH_VUS=50 BENCH_DURATION=30s make bench
```

The harness writes `meta.txt`, `monitor.csv`, `monitor-summary.txt` and `k6.txt`
under `docs/benchmarks/raw/<scenario>-<UTC timestamp>/`. The benchmark event is
reset before every scenario, so runs are independent.
